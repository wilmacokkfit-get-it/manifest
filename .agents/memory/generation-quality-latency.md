---
name: Generation quality and latency
description: Why faster reasoning is opt-in rather than the production default
---

Keep medium reasoning as the default until a repeatable comparison demonstrates
both latency benefit and preserved explicit constraints. Measure first visible
text separately from completion; do not equate a valid JSON object with a good
idea.

**Why:** A fixed synthetic comparison made low reasoning faster, but its venture
added subscriptions despite an explicit prohibition. Earlier roughly 74-second
and 20-second observations were not controlled and cannot prove a regression.

**How to apply:** Use bounded, opt-in, text-only comparisons with fixed inputs.
Never create real ventures or images merely to benchmark text. Read outputs for
intent and internal consistency before lowering reasoning or shortening quality
guidance. Communicate unknown saved state honestly when a connection fails
during a potentially successful commit.

Prompt-contract and API regression success are not evidence of factual or safe
model output. A live desk-light check still used unsupported certification
wording and placed qualified review after functional prototyping.

**Why:** Prompt instructions alone did not prevent these failures. Preserve
fictional output-quality evaluations and human inspection as a separate check;
never infer safety from well-formed JSON or an automated signal pass.

Review-order checks must recognize both “qualified engineer review” and “review
with a qualified engineer.” Planning phrases such as “define test loads” are
not themselves instructions to conduct physical tests.

**Why:** Live structural concept checks rejected drafts that contained prior
professional review because the recognizer only accepted one word order and
treated test-planning nouns as imperatives. Other drafts still made genuine
revenue or safety-sequencing errors after prompt improvements.

**How to apply:** Test equivalent review phrasings alongside actual build/load
testing commands. Keep validation hard, distinguish rejected drafts from
connection/provider stalls, and do not claim generation is fixed while live
output still fails. Log only fixed rejection codes, never raw ideas or drafts.

Internal draft correction is one bounded pass inside the original generation,
not a new submission or the visitor's optional context refinement.

**Why:** Asking creators to retry rejected AI drafts leaves the generator's own
mistakes with the user. Re-admitting work or resetting deadlines risks duplicate
ventures, extra allowances, and workers outliving their recovery leases.

**How to apply:** Preserve the request identity, name, provenance, selected Mix
mechanisms and allowance. Share the initial text deadline, validate raw and
normalized correction before saving, hide rejected build steps while correcting,
and replace the preview rather than leaving stale steps. No endless retries or
silent acceptance when a correction still fails.
